# Footage Tracker — audit and plan to make it the player hub

Written 2026-09-08. Round 1: understand it, find what is broken, decide what to add. **No code was changed.**

Sources: the whole of `frontend/src` (2,137 lines) read line by line; the original build prompt
(`PRO_PLACEMENT_FOOTAGE_TRACKER_PROMPT.docx.txt`); `future_app_guidelines.docx.txt`; the two footage guides; a live
test against the deployed Firestore database; and the vault (`phase1_foundation.md`, `phase2_visibility.md`,
`cv_guide.md`, `phase3_sop_v1.md`) for what the program actually needs from a player.

---

## 0. The one thing to read if you read nothing else

**The database is open to the whole internet.** Anyone can read every player record without logging in. I tested it:
one web request with the key that ships inside the app's own JavaScript returned **6 real player documents**, each one
carrying the player's **password in plain text**, his email, his full name and every footage link. Writes are open too
(they must be — that is how signup works today).

Nothing else in this document matters until that is fixed. And it must be fixed **before** a single passport goes in,
not after. Today the leak is footage links and passwords. With your plan it becomes passports and dates of birth.

This is the second time this exact mistake has appeared in the business: the CRM's Firestore document is also
world-readable (flagged in the Stage 3 build log). Same root cause, same fix.

## 1. What the app does today

**What it is.** A React (Vite) single-page app on Vercel, with a Firebase Firestore database. `frontend/` is the whole
thing; there is no backend of our own. Repo: `kokkinispanos/footage-tracking-app`, two commits.

**Who uses it.** A player signs up with name / email / password / position and lands on his dashboard. One admin logs
in with a shared password and sees every player.

**The five sections a player fills in** (all of them are LINKS he pastes — the app has no file upload at all):

| # | Section | What he adds | Target shown |
|---|---|---|---|
| 1 | Full Game Recordings | link, label, date, notes | 3 recommended |
| 2 | Top 3 Best Clips | link, title, skill category, why it's his best | exactly 3 slots |
| 3 | Skill Clips | link + notes, filed under 8 skill categories (5 different ones if he is a goalkeeper) | — |
| 4 | Professional Photography | one link each for the 6 photo types from the footage guide | 6 |
| 5 | Master Google Drive Folder | one link, plus the required subfolder list | 1 |

**The admin side.** `/admin` lists every player with a progress bar, search, position filter and sort.
`/admin/player/:id` shows that player's dashboard read-only, lets the admin write a general note plus a note on each
individual clip, and export his record as JSON.

**The record in the database** (`services/db.js:19-42`) is one document per player:

```
uid, password, role,
profile { fullName, email, position, createdAt },
fullGames[], topThreeClips[], skillClips{13 categories}, photos{6 types},
driveFolder{link}, adminNotes{general, perClip{}}
```

**How saving works.** Every change updates local state and, one second later, writes the **entire document** back with
`setDoc(..., {merge:true})` (`context/PlayerContext.jsx:38-58`). There is a small "Saving / Saved" pill in the header.

**How login works.** There is no Firebase Auth. `services/db.js:44-64` fetches the player's document and compares the
typed password to the stored one **in the browser**. The result — `{uid, email, role}` — is written to `localStorage`
and trusted from then on (`context/AuthContext.jsx:12-18`).

**What it is good at, honestly:** the five sections match the footage guide exactly, the empty states and the guidance
text are genuinely well done, the position-aware skill categories (goalkeeper vs outfield) are a nice touch, and the
per-clip admin notes are the right idea. The shape of the thing is right. The foundation under it is not.

## 2. What is broken

I asked the Codex CLI (GPT, `gpt-6-astra`) to audit it independently, as you asked. **It ran out of credit before it
could write its report** — it read the whole of `src/` and proved four bugs with its own test harness, then hit the
usage limit ("try again at 11:35 PM"). Its four findings are #2, #4, #5 and #7 below. I re-checked each one against the
code myself rather than take them on trust; all four are real. The rest are mine.

Ranked by what they cost you.

| # | What is wrong | Where | What actually happens |
|---|---|---|---|
| 1 | **The database is open to the internet** | `services/firebase.js` + the deployed rules | Anyone reads all 6 player records, passwords included. Details in §3. |
| 2 | **Two players editing on two devices overwrite each other** | `PlayerContext.jsx:38-58` | Every save writes the whole document. There is no live listener (`onSnapshot` appears nowhere), so a phone and a laptop open at once means the last save wins and the other's clips vanish. The guidelines you wrote demanded real-time cross-device sync; it was never built. |
| 3 | **You can only move a clip UP, never down** | `Section1FullGames.jsx:121`, `Section2TopClips.jsx:140` | `moveItem` is only ever called with `-1`. There is no down button. Worse, the button uses a drag-handle icon, so it looks like drag-and-drop and is not. Reordering is half-built. |
| 4 | **The admin cannot delete a note** | `AdminNoteField.jsx:19` | The guard `if (note === initialValue) return;` means clearing a note back to empty never saves. The note comes back on reload. |
| 5 | **Two admin notes written close together — one is lost** | `db.js:88-108` | `updateAdminNotes` reads the document, merges in memory, writes it back. Two saves that overlap (each field has its own 1-second timer) and the second erases the first. Codex reproduced this. |
| 6 | **Every autosave rewrites the player's own password and role** | `PlayerContext.jsx:50` + `db.js:76-84` | The client holds the whole document including `password` and `role` and pushes it all back. Those fields should never travel through the browser. |
| 7 | **The same player shows two different completion figures** | `Dashboard.jsx:28-31` vs `AdminOverview.jsx:11-56` | The player's bar counts clips only, out of 30. The admin's counts clips + photos + drive, out of 30. Codex tested one record: the admin sees **100%**, the player sees **77%**. You and he are looking at different numbers for the same thing. |
| 8 | **"Newest First" does not sort** | `AdminOverview.jsx:91` | `createdAt` is an ISO text string (`db.js:23`); subtracting two strings gives `NaN`, so the comparator does nothing and the list stays in whatever order Firestore returned. |
| 9 | **Nothing checks that a link works** | every section | A player pastes a Drive link that is set to private, sees a green tick, and the editor cannot open it. This is the same trap the Stage 3 assets form solved with an "I opened every link in a private window" tick box. |
| 10 | **No password reset, no email verification, no way to change email or position** | — | A player who forgets his password has to be fixed by hand in the database. Position is chosen once at signup and drives which skill categories he sees. |
| 11 | Admin notes are invisible to the player, by design | build prompt, V1 | The admin writes "trim this clip to 10 seconds" and the player never sees it. The feedback loop does not close — it was listed as a V2 feature and never built. |
| 12 | Loose ends | `index.html`, `README.md` | The browser tab says "frontend". The README is the unedited Vite template. |

## 3. Security, plainly

**How it is supposed to work:** a player types a password, the app checks it, and he sees his own record.

**How it actually works:** the app asks the database for the player's whole document *before* checking anything, and
compares the password in the browser. The database allows this because its rules let anyone read anything.

**What someone outside can do right now, with no account and no password:**

- Read every player's full record — name, email, **plaintext password**, position, every footage link, and your private
  admin notes about him. I confirmed this with a single request and got 6 real players back.
- Write to, change, or delete any player's record. (Writes must be open, or signup and autosave could not work.)
- Take the passwords and try them on those players' email accounts. People reuse passwords. This is the part that turns
  a leak into someone else's problem.

**What a logged-in player can do:** open his browser's storage, change `role` from `player` to `admin`, reload, and get
the full admin dashboard — every other player and all your notes. `AuthContext.jsx:12-18` restores that value with no
check and `App.jsx:10-25` trusts it.

**And the admin password is printed on the login page.** `Login.jsx:79-84` renders an "Admin Access (Auto-fill)" button
that types `admin@admin.com` / `adminpw123` into the form. The password is also in the shipped JavaScript
(`db.js:46`). Your own build prompt said: *"adminpw123 is for development/testing only... Do not expose the password in
client-side code comments or UI elements."* It was exposed in the UI.

**Why this matters more under your plan.** A passport is an identity document. A date of birth plus a passport scan
plus an email address is enough for someone to impersonate a player. If passports go into this database as it stands,
you are hosting an identity-theft kit for anyone who thinks to look — and these are paying clients who trusted you with
it. The fix is not optional and it is not hard: real Firebase Auth, real Firestore rules, real Storage rules.

## 4. What is missing for the app as it is

Things a player or an admin would simply expect:

- **No file upload of any kind.** Everything is a pasted URL. That was a deliberate V1 decision ("This app is about
  LINKS, not file uploads") — but it is the decision your plan changes.
- **No way to say "I'm finished."** No submit, no review state, no approve / needs-redo. The player never learns
  whether what he sent was good enough, and you have no list of who is waiting on you.
- **No deadlines and no nudges.** Nothing tells a player he is in week 5 with 4 clips.
- **Nothing on the phone.** No sticky bottom navigation, no full-screen modals on mobile, no safe-area handling —
  all of it asked for in `future_app_guidelines.docx`. He films on his phone and this is a desktop layout.
- **No offline fallback**, also asked for in the guidelines. A player on stadium wifi loses what he typed.
- **No export for the player** (guidelines: "always include a feature for the user to export their raw data"). Only the
  admin can export, as JSON.
- **No activity trail.** You cannot see when he last touched it, so "is he working?" is a guess.
- **The progress target is invented.** 30 clips, when the footage guide asks for 10–20 plus 6 photos.

## 5. What is missing for your plan — the hub

You want one place where the player puts everything about himself. Here is what "everything" actually is, taken from
the program's own documents, not made up.

### 5a. The rule that stops the three things contradicting each other

Say it in one line and it stays simple:

> **The Footage Tracker is what the player GIVES us. The website page is what CLUBS SEE. The portal is what is
> HAPPENING NOW.**

Give / show / do. Three different verbs, three different audiences. Nothing needs to move between them by hand except
by one deliberate button. The tracker is his locker; the proof page is the shop window cut from it; the portal is the
campaign. Keep it that way and nobody gets confused.

### 5b. Links or real uploads? Split it by size and sensitivity

- **Big video stays a link** — full games, raw clips, the finished reel. They are gigabytes; Drive and YouTube already
  handle it and cost nothing. Uploading these to Firebase Storage would be slow and would cost real money.
- **Small documents become real uploads** — passport, CV, headshot. A passport must **never** be a Google Drive file set
  to "anyone with the link". That is a public URL that will outlive the program. These belong in Firebase Storage,
  in the player's own folder, readable only by him and you.

One sentence to remember: **videos are links, documents are uploads.**

### 5c. What to add, grouped so it is not overwhelming

The five footage sections stay exactly as they are. Four new ones go around them.

**A. Identity & eligibility** — *this is the section that decides which countries are even possible*
- Full name exactly as written in the passport
- Date of birth, from a date picker (never free text — Stage 3's age gate fails on a mistyped date)
- Passport 1: country, expiry, **scan uploaded**
- Second passport, same
- A parent or grandparent born in the EU? which country, which relation *(this is what turned a Lane B player into a
  possible Lane A in the wave-3 test — it is the single highest-value question you ask)*
- Visa / residency status
- The three consents, each with the date he ticked it: clubs may see his email and Instagram · we may write to clubs
  from his Gmail · his payer agrees to the Monday email

**B. The player card** — *the numbers and facts that go into every club email*
- Height, weight, preferred foot
- Current club, level, registration status, contract until, **available from**
- Languages spoken
- **Measured numbers as separate fields with units** — top speed km/h, sprint distance, and the position-specific ones.
  Not one free-text box. Matthew's cell today reads `Top Speed/ 32 km/hour, Distance sprint: 120m 13seconds, 7 saves
  avr per game, 6 foot 7 tall` — that is what one free-text box produces, and it goes in front of clubs.
- Season-by-season stats: club, league, matches, goals, assists — the CV guide's Step 8
- Career history and achievements — the CV guide's Steps 5 and 6
- His own draft of the one-line headline and the 2–4 sentence summary

**C. Contact & handles**
- His email, phone with country code, WhatsApp
- Instagram handle *(he sends the club DMs from it)*
- **The Gmail the club emails will leave from** — Stage 3 needs exactly this address
- Parent / payer name and email, only with the consent tick
- Transfermarkt link

**D. Finished deliverables** — *the outputs of Phase 1, which today live nowhere*
- Highlight reel (link) — with **signed off by Panos** yes/no
- CV (uploaded PDF) — with **signed off by the player** yes/no
- Professional headshot (upload)
- His proof page link, read-only, once it exists

Those two sign-offs are two of your five Phase 1 exit criteria (`phase1_foundation.md` §8) and there is currently no
place in the world where they are recorded.

**E. One more section worth having: where he is live**

`phase2_visibility.md` line 211 says, in your own words: *"No internal tracker for which platforms each client is live
on — currently tribal knowledge per client folder."* This app is the obvious place to close that. One row per platform,
a link and a status: Transfermarkt, Wyscout, Soccerway, aiScout, Tonsser, Skouted, YouTube, Instagram, LinkedIn. The
player pastes his own links as he goes live; you see at a glance who is done. It costs one simple section and it kills
a documented gap.

### 5d. The process pieces that make it useful rather than just a bigger form

- **Submit for review, per section.** He presses it, the section locks, you get a list of what is waiting.
- **Approve / Needs redo + one line of reason, visible to him.** This is the loop that is broken today: you write "trim
  this clip" and he never reads it. It was a V2 feature that never got built, and it is the difference between a
  storage box and a working process.
- **A readiness panel** on the admin side that says, per player, exactly what is still missing before Phase 3 can
  start — passport, DOB, reel, CV, gmail, consents. So "is he ready for the attack?" is a glance, not an investigation.
- **A link check** — the "I opened every link in a private window and it works" tick, exactly as the Stage 3 assets
  form does it.

### 5e. The prize, for later — stop typing the same things twice

Look at what Stage 3 needs on the player's row and where it comes from today:

| Stage 3 needs | Where it is now | Who types it |
|---|---|---|
| `Y full_match_links` | **already in this app**, section 1 | the editor re-types it into the Tally assets form |
| `AB photo_urls` | **already in this app**, section 4 | the editor re-types it |
| `X highlight_reel_url` | nowhere | the editor |
| `Z cv_url` | nowhere | the editor |
| `AA gps_numbers` | nowhere | the editor, as free text |
| `R date_of_birth`, `F nationality`, `G lane` | the Tally intake form | the player, again |

The player already put half of it here. Then a human copies it into a different form. Once the hub holds all of it,
**one button — "send to Stage 3" — posting to the Player Intake webhook that already exists** removes that retyping
completely. That is a small, real, high-value connection, and it does not turn this app into the portal or the website.

**Do not build it until the security is fixed.** A button that pushes data into the live Stage 3 machine from an app
anyone can write to is a worse idea than the retyping.

## 6. The order I would do it in

**Round 1 — stop the bleeding (do this before anything else, and before any passport goes in)**
1. Real Firebase Auth. Delete the `password` field from every document; players reset their passwords once.
2. Real Firestore rules: a player reads and writes his own document and nothing else; the admin is a custom claim, not
   a string in `localStorage`.
3. Kill the admin auto-fill button and the hard-coded admin password.
4. Tell the 6 existing players their password should be changed anywhere else they reused it. It is not a nice email to
   send. It is a much better one than the alternative.

**Round 2 — fix what is already there**
5. Live sync (`onSnapshot`) so two devices stop overwriting each other; save fields, not the whole document.
6. The down button; note deletion; the admin-notes race; one single completion formula.
7. Link validation and the "I checked it in a private window" tick.

**Round 3 — the hub**
8. Firebase Storage with rules, for passport / CV / headshot only.
9. Sections A, B, C, D. Then E.
10. Submit for review, approve / needs redo visible to the player, and the readiness panel.

**Round 4 — the connection**
11. One "send to Stage 3" button into the Player Intake webhook.

## 7. Two decisions that are yours

1. **Do we rebuild the auth, or rebuild the app?** My answer: rebuild the auth inside this app. The five footage
   sections are good and match the guide; the shape is right. It is roughly a day of work to put a real floor under it,
   against a week to start again and lose what works.
2. **Is the CV intake form absorbed into this app?** Today `phase1_foundation.md` week 3 has the player fill a separate
   CV intake form. Sections B and C above *are* that form. If the hub holds it, that form disappears and the CV gets
   written from data you already have. I would absorb it — but it is your call, because it changes a Phase 1 step.
